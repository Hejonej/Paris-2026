# 개발용 Google 지도 연결

운영 Cloudflare 설정과 별개로, 맥북의 Expo 개발 서버에서 Google Routes API를 호출한다. Google 키는 `.afield-maps.local.json`에 권한 0600으로 보관하며 Git과 Metro 파일 제공 대상에서 제외한다. 키는 앱·GitHub·채팅에 포함하지 않는다.

## 설정과 실행

1. `npm run maps:setup` 후 http://127.0.0.1:8096 을 연다.
2. 별도 Google Cloud 개발 프로젝트에 결제 계정을 연결하고 Routes API를 활성화한다. 키의 API 제한은 Routes API로 한정하고 사용량 한도·비용 알림을 설정한다.
3. 로컬 설정 화면에 키를 저장하고 공개된 장소 주소로 조회한다.
4. `npm run start -- --tunnel --clear`로 Expo를 시작한다. `scripts/start-dev.cjs`가 개발용 연결을 활성화한다.
5. 앱의 AI 계획에서 조건 저장 후 제안받기. 주소·허용 이동수단으로 Google 거리/시간을 조회한 다음 AI에 전달한다. 제안 검토 단계까지 기존 일정은 변경하지 않는다.
6. 일정에서 `이동 시간 확인`을 누르면 해당 구간의 실제 Google 조회 결과를 표시한다. 숙소 출발·귀가 구간도 제공한다. 식사/휴식 위치가 미정이면 다음 주소가 정해진 장소까지의 참고 구간임을 표시한다.

다른 다운로드 폴더에서 실행할 경우 `AFIELD_MAPS_CONFIG_PATH` 환경변수로 이 맥북의 기존 비공개 키 파일 경로를 지정할 수 있다. 키 자체를 환경변수나 앱에 넣지 않는다.

## 계획 기준

- 숙소/공항 출발·귀가, 기존 일정, 고정 일정, 식사·휴식, 하루 속도와 체류 시간을 보호한다.
- 선택한 이동수단의 Google 방향별 실제 소요 시간에 사용자가 설정한 여유 분을 더한다. Google 경로가 없는 구간의 시간을 임의로 만들지 않는다.
- AI가 제안한 장소·일시를 엄격히 검증한다. 미배치된 선택 장소는 실제 이동 시간과 빈 시간을 이용한 별도 제약 기반 배치 단계가 보완한다. 기존 일정과 수락한 초안 항목은 이동하지 않는다. 이 단계는 추가 AI 응답으로 표시하지 않는다.
- 장소 선택을 해제하면 직전→직후의 새 연결 구간도 다시 검증한 뒤 적용한다. 선택한 제안만 적용하며 MUST 누락·충돌은 거부한다.
- 이동 설명의 숫자는 Google 자료에서 앱이 계산하며 AI가 쓴 숫자를 그대로 표시하지 않는다.
- 이것은 실제 이동 시간을 반영한 실용적 배치이며 전역 최적해를 보장하지 않는다. 주소 미정인 식사/휴식과 기존 일정의 이동, 영업시간·예약·날씨는 미확인이다. 대중교통은 조회 시점 기준이며 여행 날짜의 확정 시간표가 아니다.

## 개발 한도와 보안

한 요청에서 주소 12개와 이동수단 3개까지 비교한다. Google 행렬은 8×8 이하로 나누고 개별 오류/경로 없음은 제외한다. 서버 세션은 2,400개 요소로 제한하고 같은 행렬은 1시간 메모리 캐시한다. 구간 조회 버튼도 세션 한도에 포함된다. 구간 수에 따라 Google 이용료가 발생할 수 있다.

Expo 개발 서버에 `/afield-dev/routes`를 추가한다. Google 키 대신 제한된 개발 세션 토큰을 사용하며 인증 없는 호출은 401로 차단한다. 일반 export에서는 개발 토큰을 앱 설정에 넣지 않는다. 토큰은 개발 앱의 접속 정보이므로 운영 인증으로 사용할 수 없다. 상용 서버 배포와 사용자별 인증/한도는 별도 작업이다. 운영 Cloudflare 설정은 변경하지 않았다.

## 일본 대중교통 예외와 실패 안내

Google 공식 FAQ에 따르면 Routes API는 일본 대중교통을 지원하지 않는다(https://developers.google.com/maps/faq#transit_directions_countries). Google Maps 소비자 앱과 API 제공 범위는 같지 않다. 일본 여행 검토 화면에 이 제한을 표시한다.

도보와 대중교통을 함께 선택하면 30분을 넘는 도보 구간을 대중교통 미조회 결과의 대체값으로 자동 사용하지 않는다. 실제 대중교통 응답이 있으면 그 수단을 사용한다. 사용자 선택이 도보만이면 해당 도보 결과는 유지한다. 별도 일본 교통 제공자 연결 전에는 긴 구간의 실제 전철 시간을 확정할 수 없다. 임의의 시간을 실제 값으로 만들지 않는다.

기존 일정끼리의 미확인 경로는 새 장소와 무관한 삽입 위치의 점수 전체를 무한대로 만들지 않는다. 새 장소에 인접한 실제 경로의 검증은 계속 적용한다. 자동 보완 검색이 실패하면 전체 검토 기간/일수/후보 시간 수와 실패 요약을 표시하며 AI가 처음 시도한 한 자리의 실패 구간을 전체 배치 불가 이유처럼 사용하지 않는다.

## 2026-11-16 웹 동선 구성 복원

비교 근거는 웹 app-core.html의 optimizeWithGoogle(`/optimize-trip`), hkm, enrichPlanLayers다. 웹은 위치가 가까운 장소를 날짜/동선에 묶는 단계와 상세 이동시간을 다루는 단계가 구분되어 있었으나 초기 모바일은 고정 시간 삽입 검증에 치우쳐 있었다.

모바일 개발 서버는 선택 장소의 주소를 Google Routes로 해석해 Google place ID/좌표를 확인한 다음 기존 웹 계산 API에 동선 그룹을 요청한다. 부분 일치 주소는 임의로 확정하지 않는다. 공개 도쿄 2곳/2일 테스트는 HTTP 200이었고 같은 날 여러 곳인 테스트는 Google API 400을 포함한 HTTP 502를 반환했다. 운영 서버는 변경하지 않았다. 그 경우 웹 클라이언트의 거리 함수/가까운 장소 묶기와 방문 순서 구성을 개발 서버에 이식한 경로를 사용하며, 결과 출처를 `web_local_geographic_grouping`으로 구분한다. 실제 교통시간을 얻었다고 표시하지 않는다.

지역별 그룹은 제안용 힌트다. 모바일에서는 숙소/공항 출발·귀가, 기존 일정, 예약, MUST와 식사 시간을 보존한 상태에서 후보 시간/삽입 위치를 비교한다. 아직 수락하지 않은 AI 초안의 순서는 다시 검토할 수 있으며 이미 저장한 사용자 일정은 재배치하지 않는다. 위치 간 거리 비용으로 불필요한 이동을 줄이되 수학적 전역 최적해를 보장하지 않는다.

대중교통이 선택되어 있고 두 위치 사이 도보 경로는 확인되지만 긴 도보를 대체할 실제 대중교통 시간이 없으면, 배치안에 `pendingTransfers`를 표시한다. 검토용 이동 슬롯 30분과 사용자가 정한 여유 분은 실제 교통시간이 아니다. 구간 양 끝과 Google Maps 대중교통 링크를 제공하며, 선택한 구간을 다시 계산한 뒤 명시적 임시 적용 확인이 있어야 저장할 수 있다. 확인하지 않은 상태의 store/pure apply도 거부한다. 적용된 장소는 `needsTransitCheck`로 표시하며 재실행해도 남는다. 실제 일본 전철·버스 시간의 자동 조회는 여전히 별도 공급자가 필요하다. 새 서비스 계정/유료 구독은 추가하지 않았다.

## 2026-11-16 일반 방문 시간 유동화

일반 장소는 방문 순서/제안 도착 시각만 가진다. 장소별 고정 체류시간 입력과 표시, 자동 60분 블록, 이전 `durations` 설정의 배치 제약을 제거했다. 기존 저장 필드는 호환성을 위해 보존하지만 일반 방문의 끝나는 시각을 계산하는 데 사용하지 않는다. 새 일반 방문에는 `durationMinutes`를 쓰지 않는다. AI 요청에도 장소별 체류 분을 전달하지 않으며 legacy durations는 빈 값으로 보낸다.

점심·저녁·휴식은 희망 시각 표시로 다루고 60/30분 점유 구간을 생성하지 않는다. 실제 예약·항공편·숙소 수속 구간은 계속 보호한다. 일반 방문의 기존 시각과 MUST는 이동하거나 삭제하지 않는다. 이동 시간/여유와 실제 예약의 시간 겹침 검사는 유지한다. 과거 검토 결과는 이전 기준임을 표시하고 새로 생성하도록 안내한다.

합성 여행에서 기존 18개 일정과 이전 60분/240분 설정이 있어도 새 미정 장소의 배치가 가능한지 검증했으며, 원본 18개 항목은 변경하지 않았다. 이는 사용자 기기의 실제 여행을 추출한 테스트는 아니다.
